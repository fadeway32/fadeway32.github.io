1. Kubernetes 是什么，解决什么问题？

面试结论：

Kubernetes 是一个容器编排平台，用来管理容器化应用的部署、调度、扩缩容、服务发现、故障自愈和滚动发布。它解决的是大规模容器应用“怎么部署、怎么运行、怎么发现、怎么恢复”的问题。

K8s 本质是一个声明式的容器编排系统。用户描述期望状态，比如我要 3 个副本，K8s 控制器不断把实际状态调整到期望状态。它不是简单运行 Docker，而是提供了调度、自愈、服务发现、发布、扩缩容等完整平台能力。

为什么不直接调度容器？

因为有些容器天然需要强绑定，比如业务容器 + sidecar 日志采集、业务容器 + service mesh proxy，它们需要部署在同一台机器、共享网络和生命周期。

5. QoS 分类

面试结论：

K8s 根据 requests 和 limits 把 Pod 分成 Guaranteed、Burstable、BestEffort 三类，节点资源紧张时，BestEffort 最容易被驱逐，Guaranteed 最稳定。

QoS 条件 稳定性
Guaranteed 每个容器 CPU/Memory 都设置 request=limit 最高
Burstable 设置了部分 request/limit，但不完全相等 中等
BestEffort 没有设置 request/limit 最低

驱逐优先级大致是：

标准表达：

生产服务一般不要裸跑 BestEffort，至少要设置 requests。核心服务可以考虑 Guaranteed，但资源利用率会低一些；大部分业务服务通常是 Burstable，在稳定性和资源利用率之间平衡。

6. 探针：liveness、readiness、startup

面试结论：

liveness 判断容器是否需要重启，readiness 判断 Pod 能不能接流量，startup 判断应用是否启动完成，避免慢启动应用被 liveness 误杀。

探针 作用 失败后果
livenessProbe 判断应用是否活着 失败会重启容器
readinessProbe 判断是否可以接流量 失败会从 Service Endpoints 摘除
startupProbe 判断启动是否完成 成功前禁用其他探针

典型链路：

标准表达：

readiness 影响流量，liveness 影响重启。不能用 liveness 代替 readiness，否则应用只是临时不可用也会被重启，反而扩大故障。

K8s 和 Spring Cloud 有能力重叠，但层次不同。K8s 偏基础设施编排，Spring Cloud 偏应用层微服务治理。

8. 架构面试综合回答模板

如果面试官问：“你们 Java 微服务怎么落地 K8s？”

可以这样答：

我们一般用 Deployment 部署无状态 Java 服务，通过 Service 提供稳定访问入口，外部流量走 Ingress 或 API Gateway。配置通过 ConfigMap/Secret 注入，动态业务配置保留 Nacos/Apollo。服务发现优先使用 K8s Service 和 CoreDNS，应用层限流熔断可以继续使用 Sentinel 或 Resilience4j。

生产上每个服务都要配置 requests/limits、readiness/liveness/startupProbe，并支持 SIGTERM 优雅停机。发布使用 Deployment 滚动更新，核心服务设置 maxUnavailable=0，并配合 PDB、反亲和和 HPA 保证可用性。日志输出到 stdout，由 DaemonSet 采集到日志系统，指标用 Prometheus/Grafana，链路追踪用 OpenTelemetry 或 SkyWalking。

权限上使用 RBAC 和独立 ServiceAccount，环境隔离通过 namespace 或独立集群实现，核心生产环境会配 ResourceQuota、NetworkPolicy、镜像扫描和 Secret 加密。整体目标是让服务不仅能跑，还要能稳定发布、快速排查和安全治理。

9. 常见追问

第七轮总结：

K8s 生产实践的核心是把应用、平台和治理能力结合起来。Java 微服务用 Deployment/Service/Ingress 跑起来只是第一步，真正要考虑的是配置管理、服务发现、滚动发布、弹性扩缩容、优雅停机、日志监控链路追踪、RBAC 权限、安全策略和多环境隔离。高级面试里要体现一点：K8s 是基础设施平台，不是业务治理银弹，很多能力仍然需要和网关、配置中心、Service Mesh、监控体系、DevOps 流程一起落地。

回答k8s所有的常见追问的问题

20:54

下面给你一版 K8s 常见追问速答版，适合面试前快速过一遍。每题都是“能直接说出口”的标准回答。

一、基础核心追问

1. Pod 和容器有什么区别？
容器是实际运行进程的环境，Pod 是 K8s 最小调度单位，一个 Pod 可以包含一个或多个容器，Pod 内容器共享网络和 Volume。

2. Deployment 和 ReplicaSet 什么关系？
Deployment 管理 ReplicaSet，ReplicaSet 管理 Pod 副本。平时直接使用 Deployment，因为它支持滚动更新和回滚。

3. Deployment 和 StatefulSet 区别？
Deployment 适合无状态服务，Pod 名称和存储不稳定；StatefulSet 适合有状态服务，提供稳定名称、稳定网络身份和稳定 PVC。

4. Service 为什么需要 selector？
Service 通过 selector 匹配一组 Pod Label，从而把流量转发给这些 Pod。没有 selector，Service 不知道后端是谁。

5. Service 和 Ingress 区别？
Service 解决集群内稳定访问和负载均衡，Ingress 解决外部 HTTP/HTTPS 七层入口路由。

6. ConfigMap 修改后 Pod 会自动更新吗？
如果以环境变量注入，不会自动更新；如果以 Volume 挂载，文件内容可能更新，但应用不一定自动 reload。

7. Secret 是不是安全的？
Secret 默认只是 Base64 编码，不是加密。生产要配合 RBAC、etcd 加密、KMS/Vault 和权限控制。

8. DaemonSet 适合什么场景？
适合每个 Node 都要运行一个实例的场景，比如日志采集、监控 Agent、CNI 插件、存储插件。

9. Namespace 能不能实现强隔离？
Namespace 是逻辑隔离，不是强安全隔离。强隔离还要配合 RBAC、NetworkPolicy、ResourceQuota，甚至独立集群。

10. K8s 为什么是声明式系统？
用户声明期望状态，比如副本数为 3，K8s 控制器持续对比实际状态并自动调谐到期望状态。

二、Pod 生命周期与调度

1. Pod Pending 一般是什么原因？
常见是资源不足、PVC 未绑定、节点污点不可容忍、亲和性不满足、Node NotReady 或 ResourceQuota 不足。

2. requests 和 limits 哪个影响调度？
requests 影响调度，scheduler 根据 requests 判断节点资源是否足够；limits 是运行时资源上限。

3. CPU 超限和内存超限有什么区别？
CPU 超 limit 通常被限流，表现为变慢；内存超 limit 可能被 OOMKilled，容器会被杀掉重启。

4. readiness 和 liveness 区别？
readiness 判断 Pod 能不能接流量，失败会从 Service 后端摘除；liveness 判断容器是否存活，失败会重启容器。

5. 为什么需要 startupProbe？
用于保护启动慢的应用，在 startupProbe 成功前不会执行 liveness，避免应用还没启动完就被误杀。

6. Scheduler 会不会启动容器？
不会。Scheduler 只负责给 Pod 选择 Node，真正启动容器的是目标节点上的 kubelet。

7. OOMKilled 是谁杀的？
通常是容器内存超过 cgroup limit 后，被内核 OOM killer 杀掉，K8s 再根据重启策略拉起容器。

8. QoS 有什么用？
QoS 影响节点资源紧张时的驱逐优先级，BestEffort 最容易被驱逐，Guaranteed 最稳定。

三、K8s 网络

1. Pod IP 和 Service IP 有什么区别？
Pod IP 是具体 Pod 的真实地址，会变化；Service IP 是稳定虚拟入口，用来负载均衡到后端 Pod。

2. ClusterIP 是真实 IP 吗？
ClusterIP 是虚拟 IP，不对应某个真实网卡，流量由 kube-proxy 的 iptables/IPVS 规则转发到 Pod。

3. kube-proxy 是不是转发所有流量？
不是。kube-proxy 主要维护 Service 转发规则，真正数据转发由内核规则完成。

4. iptables 和 IPVS 模式区别？
iptables 基于规则链 DNAT，规模大时规则多；IPVS 基于内核 LVS，支持更多负载算法，大规模场景更稳定。

5. Ingress 和 Service 区别？
Service 是服务访问抽象，偏四层；Ingress 是 HTTP/HTTPS 入口规则，偏七层，需要 Ingress Controller 执行。

6. 为什么有了 Service 还需要 Ingress？
Service 解决集群内访问，Ingress 解决外部域名、路径、HTTPS、七层路由等入口能力。

7. CoreDNS 怎么解析 Service？
CoreDNS 监听 K8s Service 和 EndpointSlice，把 service.namespace.svc.cluster.local 解析成 ClusterIP。

8. Headless Service 有什么用？
Headless Service 不分配 ClusterIP，DNS 直接返回后端 Pod IP，常用于 StatefulSet 和需要访问具体 Pod 的场景。

9. CNI 负责什么？
CNI 负责给 Pod 分配 IP、创建网络设备、配置路由和网络策略，实现 Pod 间通信。

10. NetworkPolicy 为什么不生效？
常见原因是 CNI 不支持 NetworkPolicy、selector 写错、namespace 选错、策略方向 ingress/egress 配错。

四、存储与配置

1. Volume 和 PV/PVC 区别？
Volume 是 Pod 内挂载抽象；PV 是集群存储资源；PVC 是应用对存储资源的申请。

2. PVC 一直 Pending 是什么原因？
可能没有匹配 PV、StorageClass 不存在、动态 provisioner 异常、容量/访问模式不匹配。

3. StorageClass 有什么作用？
StorageClass 定义动态存储供给模板，PVC 可以通过它自动创建对应 PV 和底层存储。

4. RWO、ROX、RWX 区别？
RWO 单节点读写，ROX 多节点只读，RWX 多节点读写。多副本共享写通常需要 RWX 存储。

5. StatefulSet 为什么适合有状态服务？
因为它提供稳定 Pod 名称、稳定 DNS、稳定 PVC，以及有序启动和删除。

6. Headless Service 和 StatefulSet 什么关系？
Headless Service 给 StatefulSet 每个 Pod 提供稳定 DNS，比如 mysql-0.mysql.default.svc.cluster.local。

7. ConfigMap 更新后应用会自动生效吗？
环境变量不会自动变；Volume 文件可能更新，但 Java 应用通常仍需要 reload 机制或重启。

8. Secret 是不是加密的？
默认不是加密，只是 Base64 编码；需要开启 etcd 静态加密并配合 RBAC/KMS。

9. hostPath 为什么生产慎用？
hostPath 绑定宿主机路径，可移植性差，安全风险高，Pod 调度到其他节点可能无法使用同样数据。

10. 数据库能不能跑在 K8s？
可以，但要谨慎。核心难点是存储性能、备份恢复、主从切换、故障处理和 Operator 运维能力。

五、发布、扩缩容、高可用

1. Deployment 滚动更新底层怎么做？
Deployment 创建新的 ReplicaSet，逐步增加新 Pod，减少旧 Pod，直到全部切换到新版本。

2. maxSurge 和 maxUnavailable 怎么配置？
核心服务常用 maxUnavailable=0 保证可用副本不减少，maxSurge=1 或百分比允许临时多起 Pod。

3. 蓝绿和金丝雀区别？
蓝绿是两套环境一次性切流，回滚快但资源成本高；金丝雀是小流量逐步放量，风险更低。

4. HPA 扩容依据是什么？
可以基于 CPU、内存、自定义指标或外部指标；CPU HPA 依赖 Pod 的 requests.cpu。

5. HPA 和 Cluster Autoscaler 谁先触发？
HPA 先扩 Pod；如果节点资源不够导致 Pod Pending，Cluster Autoscaler 再扩 Node。

6. VPA 为什么可能导致 Pod 重启？
因为 VPA 调整 requests/limits 通常需要重建 Pod，运行中的容器资源规格不能总是原地修改。

7. PDB 能不能防止节点宕机？
不能。PDB 只能约束自愿中断，比如 drain、升级，不能阻止机器故障、断电、OOM。

8. replicas=3 是否一定高可用？
不一定。如果 3 个 Pod 都在同一 Node 或同一可用区，节点故障仍会全挂，需要反亲和和拓扑分布。

9. 如何做到 Java 服务不停机发布？
配置 readiness 摘流、滚动更新、maxUnavailable=0、优雅停机、SIGTERM 处理、preStop 缓冲和合理探针。

10. readiness 和优雅停机有什么关系？
Pod 终止前 readiness 变失败，Service 不再转发新流量，应用再处理完存量请求后退出。

六、故障排查

1. Pending 和 CrashLoopBackOff 区别？
Pending 是 Pod 还没成功调度或启动；CrashLoopBackOff 是容器启动后反复崩溃。

2. CrashLoopBackOff 为什么看 –previous？
因为当前容器可能已经重启，崩溃原因在上一次容器日志里。

3. ImagePullBackOff 常见原因？
镜像地址错误、tag 不存在、私有仓库认证失败、节点网络不通、镜像仓库限流。

4. OOMKilled 和 JVM OOM 区别？
OOMKilled 是容器超过 cgroup 内存限制被系统杀；JVM OOM 是 JVM 堆或元空间等内部内存不足抛异常。

5. Service Endpoints 为空说明什么？
通常是 selector 没匹配到 Pod，或者 Pod 没 Ready，也可能是命名空间或 Label 写错。

6. Ingress 502 和 504 区别？
502 偏上游不可达、连接失败或响应异常；504 偏上游响应超时。

7. Node NotReady 常见原因？
kubelet 异常、containerd 异常、磁盘满、内存压力、CNI 异常、节点到 apiserver 网络不通、证书问题。

8. Pod Running 但服务不通怎么排查？
看 readiness、容器端口监听、Service selector、Endpoints、targetPort、NetworkPolicy、CoreDNS 和 Ingress 日志。

9. readiness 失败会发生什么？
Pod 会从 Service Endpoints 中摘除，不再接收新流量，但容器不会因为 readiness 失败而自动重启。

10. CPU 高怎么定位到具体线程？
先 kubectl top 找 Pod，再进入容器用 top -H 找线程，转换线程 ID 后用 jstack 定位 Java 线程栈。

七、架构与生产实践

1. K8s 能不能替代 Spring Cloud？
不能简单替代。K8s 管部署、调度、服务发现、弹性；Spring Cloud 更偏应用层配置、熔断、限流、网关等治理。

2. Java 服务上 K8s 要注意什么？
注意 JVM 容器内存、requests/limits、探针、优雅停机、日志 stdout、配置解耦和 HPA 指标。

3. ConfigMap 和 Nacos 怎么取舍？
ConfigMap 适合环境级静态配置；Nacos/Apollo 适合动态业务配置和运行时热更新。

4. 服务发现用 K8s Service 还是注册中心？
集群内基础服务发现可以用 K8s Service/CoreDNS；复杂应用治理或跨集群场景可保留注册中心。

5. 如何做日志采集？
应用日志输出 stdout/stderr，由 DaemonSet 日志 Agent 如 Fluent Bit/Filebeat 采集到 ES、Loki 或 Kafka。

6. Prometheus 采集哪些指标？
采集 Node、Pod、容器、K8s 对象状态、应用业务指标、JVM 指标、接口耗时和错误率。

7. RBAC 怎么设计？
按最小权限原则，区分 namespace、角色和 ServiceAccount，避免默认账号和 cluster-admin 滥用。

8. Namespace 是不是强隔离？
不是。Namespace 是逻辑隔离，强隔离需要 RBAC、NetworkPolicy、ResourceQuota，生产关键环境最好独立集群。

9. 生产环境为什么要 requests/limits？
requests 保证调度和基础资源，limits 防止单个容器打爆节点；不配置会影响稳定性和 HPA/QoS。

10. 如何做到不停机发布？
依靠多副本、readiness、滚动更新、优雅停机、PDB、反亲和、灰度发布和快速回滚机制共同保证。
