第一轮：TCP/UDP 核心。这一轮重点是网络面试里命中率最高的一组题。

1. TCP 和 UDP 区别

面试结论：

TCP 是面向连接、可靠、有序、面向字节流的传输协议；UDP 是无连接、不保证可靠、不保证顺序、面向报文的传输协议。TCP 适合可靠传输场景，UDP 适合低延迟、可容忍丢包的场景。

核心对比：

对比项 TCP UDP
连接 面向连接 无连接
可靠性 可靠传输 不保证可靠
顺序 保证有序 不保证有序
数据边界 字节流，无消息边界 报文，有消息边界
开销 较大 较小
速度 相对慢 相对快
典型场景 HTTP、HTTPS、MySQL、Redis DNS、直播、游戏、语音视频

标准表达：

TCP 把可靠性交给传输层，应用开发简单，但协议开销更大；UDP 把可靠性选择权交给应用层，延迟低、灵活性高，所以适合实时通信、音视频、游戏、DNS 这类场景。

标准表达：

3. TCP 三次握手

面试结论：

三次握手的核心目的是确认客户端和服务端的发送、接收能力都正常，并同步双方的初始序列号。

流程图：

为什么不是两次？

如果只有两次，服务端无法确认客户端是否具备接收能力。

更关键的是，历史失效连接请求可能导致服务端误建立连接。

第三次 ACK 可以让客户端确认这个连接是否真实有效。

标准表达：

三次握手不是为了形式上多一次，而是为了让双方都确认彼此的收发能力，并交换初始序列号。两次握手服务端无法确认客户端的接收能力，也更容易受到历史重复 SYN 的影响。

4. TCP 四次挥手

面试结论：

四次挥手是因为 TCP 是全双工协议，客户端和服务端两个方向的数据通道需要分别关闭。

流程图：

为什么握手是三次，挥手是四次？

因为连接建立时，服务端可以把 SYN 和 ACK 合并发送。

断开连接时，被动关闭方收到 FIN 后，可能还有数据没发完，所以通常先回 ACK，等数据发送完后再发 FIN。

标准表达：

TCP 是双向通信，关闭一个方向不代表另一个方向也关闭。主动方发 FIN 只是表示自己不再发送数据，但仍然可以接收数据；被动方处理完剩余数据后，再发送 FIN，所以通常需要四次挥手。

2. TCP 拥塞控制是什么？

面试结论：

流量控制是保护接收方，拥塞控制是保护网络。拥塞控制通过动态调整拥塞窗口，避免发送方把网络链路打爆。

快速重传：

如果发送方连续收到 3 个重复 ACK，认为某个包丢了，不等超时，立即重传。

快速恢复：

发生快速重传后，不直接把窗口降到 1，而是降低到一定值继续传输，避免吞吐量骤降。

标准表达：

TCP 拥塞控制的核心是根据丢包、延迟、ACK 等信号判断网络是否拥塞，然后调整拥塞窗口。慢启动负责探测带宽，拥塞避免负责平稳增长，快速重传和快速恢复负责在丢包时尽快恢复传输。

1. HTTP 和 HTTPS 区别

面试结论：

HTTP 是明文传输协议，HTTPS 是在 HTTP 和 TCP 之间加入 TLS/SSL 安全层，解决数据加密、身份认证和完整性校验问题。

核心区别：

对比项 HTTP HTTPS
安全性 明文传输 加密传输
默认端口 80 443
证书 不需要 需要 CA 证书
身份认证 无 可验证服务端身份
数据完整性 弱 防篡改
性能 握手简单 多 TLS 握手和加解密开销

HTTPS 解决的三个问题：

标准表达：

HTTPS 不是一种新的应用层协议，它本质上还是 HTTP，只是在 HTTP 和 TCP 之间增加 TLS 层。TLS 提供加密、证书认证和完整性校验，所以可以防窃听、防冒充、防篡改。

2. HTTPS 为什么既用非对称加密又用对称加密？

面试结论：

非对称加密用于身份认证和密钥协商，对称加密用于后续数据传输。因为非对称加密安全但慢，对称加密快但需要先安全交换密钥。

两者区别：

类型 特点 用途
对称加密 同一个密钥加密解密，速度快 加密业务数据
非对称加密 公钥加密、私钥解密，速度慢 身份认证、交换密钥
哈希/摘要 不可逆，验证完整性 防篡改

直观流程：

为什么不全程用非对称加密？

因为太慢，计算成本高，不适合大量业务数据传输。

为什么不直接用对称加密？

因为一开始客户端和服务端没有共享密钥，密钥怎么安全传过去是问题。

标准表达：

HTTPS 是组合拳。非对称加密解决“如何安全地协商密钥”和“如何证明服务器身份”，对称加密解决“高效传输大量数据”。这就是安全性和性能的平衡。

9. epoll 常见面试追问

追问 1：epoll_wait 是不是 O(1)？

更严谨地说：

epoll_wait 不需要遍历所有监听 fd，它的成本主要和就绪事件数量有关。所以不能简单说永远 O(1)，更准确是接近 O(ready events)。

追问 2：epoll 一定比 select 快吗？

不一定。

如果 fd 很少，select/poll 简单直接，差距不明显。

如果大量连接但活跃连接少，epoll 优势明显。

追问 3：epoll 的红黑树是干什么的？

红黑树保存所有被监听的 fd，用于 epoll_ctl 的增删改查；真正让 epoll_wait 高效的是就绪队列。

18. 百万 WebSocket 面试标准回答

可以直接这样讲：

百万 WebSocket 不能让业务服务直接维护连接，我会把系统拆成连接接入层、消息路由层和业务层。WebSocket Gateway 只负责长连接、鉴权、心跳和推送；业务服务产生消息后写 MQ；消息路由服务根据 userId 到 Gateway 的映射找到连接所在节点，再把消息投递到对应 Gateway。

单机容量要根据 fd、内存、socket buffer、心跳 QPS 和 EventLoop 延迟评估，通常不会追求单机扛百万，而是多节点水平扩展。LB 要支持 WebSocket 长连接，节点下线要先摘流再让客户端重连，避免重连风暴。监控上重点看连接数、重连率、ACK 延迟、MQ 堆积、Redis 延迟和节点连接分布。

最后一句压轴：

这类系统的关键不是“能连上”，而是连接状态可治理、消息可路由、故障可恢复、扩容不雪崩。
